메이플 인벤 등 커뮤니티를 보면 종종 나오는 불만이 있다. "왜 경매장은 마을에서만 이용 가능하고, 사냥터에서는 안 되는가?" 공식적으로 밝혀진 이유는 없지만, 사냥하면서 메소 먹는 자석펫을 보다 보니 왠지 모르게 DB 동시성 제어랑 분산 시스템 기준으로 설명이 될것같다.

## 사냥터와 마을의 트래픽 특성 차이
![](/assets/images/Pasted image 20260805223842.png)

사냥터는 몬스터 킬, 드랍, 경험치·골드 갱신 등 **쓰기(write) 트래픽이 극도로 높은** 구간이다. 반면 경매장 거래는 빈도는 낮지만 **강한 일관성**이 요구되는 트랜잭션. 실제로 필드에서 사냥 중인 화면을 보면, 몬스터를 잡을 때마다 메소주머니가 드랍되고 그 하나하나가 캐릭터의 메소 잔액에 실시간으로 `+=` 된다. 콤보 카운트가 200을 넘는 구간이면 이 증분 연산이 초당 여러 번 발생하는 셈.

이걸 SQL로 단순화하면 다음과 같다.

```sql
UPDATE character SET meso = meso + N WHERE char_id = ?;
```

이 자체는 원자적 연산이라 크게 문제될 건 없다. 문제는 **이 고빈도 쓰기 구간에 훨씬 무거운 트랜잭션(경매장 구매)이 겹칠 때**부터다.

## 경매장 구매는 전형적인 Lost Update 문제

경매장 구매를 단일 DB 트랜잭션으로 단순화하면 이런 모양이 된다.

```sql
BEGIN;
SELECT meso FROM character WHERE char_id = ? FOR UPDATE;  -- 잔액 확인, 행 락 획득
-- 잔액 >= 가격 체크
UPDATE character SET meso = meso - price WHERE char_id = ?;
INSERT INTO inventory (...) VALUES (...);
UPDATE auction_item SET status = 'sold' WHERE item_id = ?;
COMMIT;
```

이 트랜잭션은 여러 테이블을 건드리고 체크 로직도 들어가니, **락을 잡고 있는 시간이 길다.** 그 사이 필드에서 계속 들어오는 pickup UPDATE들이 같은 행(같은 char_id)에 락 경합을 일으키면, 짧은 pickup 트랜잭션들이 큰 구매 트랜잭션 뒤에서 대기하다 사냥 중 렉이 나거나, 반대로 구매 트랜잭션이 밀릴 수 있다.

그리고 다른 유저들이 경매장에서 경쟁하고 있기 때문에 트랜잭션 race condition도 자주 일어나고, 해당 트랜잭션이 경합이 자주 일어나면 그 여파로 사냥터에서 메소를 주워먹는 액션에도 경합이 생길 수 있다

같은 락 경합 문제가 이론적으로는 마을에서도 발생할 수 있다. 하지만 마을은 메소 잔액이 사실상 정적인 구간이고, 필드는 초당(극단적으로 메소 안먹으면 사라지는 시간 2분, 1젠에 8초, 젠당 33마리라고 치면 초당 메소주머니를 100개씩 먹을 수도 있음) 다발적으로 같은 행에 쓰기가 계속 밀리고 있다. 같은 코드, 같은 락 전략이라도 요청 빈도가 다르면 경합 확률이랑 큐잉 지연은 완전히 달라진다. 그러니 신 창섭 선생님의 입장에서는 "고빈도 쓰기 구간에서는 무거운 트랜잭션을 원천 차단"하는 게 안전한 선택이 된다.

여기서 흥미로운 점은, 사냥터에서 막혀 있는 게 경매장뿐만이 아니라는 것이다. 캐시샵을 제외한 일반 상점(캐시샵은 원래도 별도 공간으로 이동하므로) - 안드로이드(로봇) 상점, 잡화 상점, 이벤트 상점 - 역시 사냥터에서는 이용할 수 없고 마을에서만 열린다. 이걸 보면 단순히 "경매장 하나"를 막은 게 아니라, **메소 잔액을 차감(-)시키는 모든 경로를 사냥터에서 원천 차단**한 것 아닐까 싶다. 그렇게 보면 이건 경매장 하나의 문제가 아니라 "메소 잔액 감소 트랜잭션 전반"에 적용된 일관된 설계 원칙이었을 가능성이 높다.

## MSA 구조라면 문제는 더 커진다 - "락을 잡은 채로 네트워크 IO"

위 설명을 보면 경매장 ROW와 개인 인벤토리 ROW의 트랜잭션 경합으로 설명했다. 

메이플스토리는 이번 여름 업데이트에서 경매장 서버를 새로 구성했다고 한다. (이 새로 구성된 서버가 크레이지아케이드 섭종하면서 떼온 서버라는 썰이 있지만 설마..) 
경매장이 캐릭터 서비스와 물리적으로 분리된 MSA 구조라는 건데, 이 경우 문제의 핵심은 **"락을 잡은 채로 원격 서비스 응답을 기다린다"**는 데 있다.

```
[캐릭터 서비스] SELECT meso FOR UPDATE (락 획득)
  ↓ (네트워크 호출: 경매장 서비스에 구매 가능 여부 확인)
[경매장 서비스] 재고 확인, 판매자 정산 처리
  ↓ (응답 대기)
[캐릭터 서비스] UPDATE meso -= price, COMMIT (락 해제)
```

같은 프로세스 안에서 처리되는 트랜잭션의 락 보유 시간은 마이크로초~밀리초 단위지만, 락을 잡은 채 원격 호출 응답을 기다리는 구조라면 락 보유 시간이 **네트워크 왕복 시간(RTT) + 상대 서비스 처리 시간**만큼 늘어난다. 분산 시스템 설계에서 교과서적으로 피해야 하는 안티패턴("hold lock across a remote call")이다. 그 사이 같은 캐릭터 행에 대한 pickup 트랜잭션들은 전부 큐잉되는 거고.

## 실패 시 롤백은 단순하지 않다 - 2PC와 Saga

단일 DB 트랜잭션이면 실패 시 `ROLLBACK` 한 줄로 끝난다. 하지만 캐릭터 서비스와 경매장 서비스가 분리된 MSA라면 이건 분산 트랜잭션이고, 선택지는 두 가지뿐.

- **2PC(Two-Phase Commit)**: 두 서비스가 모두 "준비 완료"할 때까지 락을 유지 → 락 보유 시간이 더 늘어나 위 문제를 악화시킨다.
- **Saga 패턴(보상 트랜잭션)**: 각 서비스가 로컬 커밋을 먼저 하고, 실패 시 반대 방향으로 취소 이벤트를 발행해 되돌린다 (메소 차감 → 아이템 지급 실패 → 메소 환불 이벤트).

Saga는 락 보유 시간을 줄여주지만, 메소가 이미 빠지고 아이템은 아직 지급되지 않은 그 찰나에 필드처럼 초당 쓰기가 몰리는 구간에서는 **일시적 불일치(eventual consistency 윈도우)**가 훨씬 자주, 훨씬 눈에 띄게 노출될 수 있다.

## Saga/이벤트 기반 처리의 근본적 한계 - 유실 방지와 "체감 지연 없음"은 다른 문제

Kafka 같은 오프셋 기반 스트림으로 이벤트 유실 자체는 막을 수 있다. 근데 **유실 방지(durability)와 "언제부터 이 값을 신뢰해도 되는가(read timing)"는 완전히 별개의 문제**다. 오프셋으로 최종적으로는 정확한 값에 도달한다는 보장은 되지만, 그 "최종적으로"가 유저 입장에서는 몇백 ms에서 몇 초 사이 잔액이 오락가락하는 창(window)으로 보인다.

24년 된 게임인 메이플스토리에서 메소주머니 pickup은 "때리면 즉시 반영된다"는 동기적 인과관계를 오랫동안 학습시켜온 경험이다. 경매장을 Saga/이벤트 기반으로 만드는 순간, 캐릭터 메소 값은 단일 소스의 진실이 아니라 **여러 이벤트가 비동기로 수렴해가는 값**이 된다. SNS의 좋아요 카운트처럼 낙관적으로 먼저 보여주고 나중에 보정하는 패턴과 유사한데, 메소는 표시값이 아니라 유저의 실제 자산이라는 점에서 체감 임팩트가 다르다.

- 메소주머니를 먹었는데 잔액이 순간적으로 안 바뀌면 "버그인가" 하는 불안감
- 구매 실패로 보상 트랜잭션이 지연되며 이미 차감된 메소가 잠깐 사라졌다 다시 채워지는 걸 목격
- 그 사이 다른 pickup이 겹치면서 잔액이 튀는(jitter) 현상

분산 시스템 입장에서는 정상 동작(eventual consistency)인데 유저 입장에서는 그게 아닌 거다. 24년 동안 "때리면 즉시 반영"이 당연했던 시스템에서 갑자기 잔액이 어색하게 오락가락하면, "왜 자꾸 액수가 바뀌지?"가 먼저 나올 거고, 이게 쌓이면 문의가 온다.

## "인메모리 카운터 + 비동기 flush"는 해법이 아니다

"메소를 인메모리 카운터로 관리하고 비동기로 DB에 flush하면 되지 않냐"는 생각도 있을 수 있다. 근데 이건 안일한 접근이다.

일반적인 DB 트랜잭션은 "커밋되기 전까지는 아무도 그 값을 보지 못하고, 커밋 실패 시 그냥 없었던 일이 된다(rollback은 항상 안전)"는 보장을 준다. 인메모리 카운터 방식은 이 전제를 깨뜨린다.

```
[t0] pickup → 인메모리 카운터 += N (이미 "현재 값"으로 취급)
[t0] 화면 즉시 반영, 경매장 잔액 체크도 이 값을 참조
[t1] 비동기 DB flush 시도 → 실패
```

t0 시점에 이미 인메모리 값이 사실상의 진실로 소비되어버린다. 만약 경매장이 이 값으로 구매를 승인해버렸다면, 나중에 flush가 실패해도 **이미 되돌릴 수 없는 다운스트림 액션(구매 승인)이 나가버린 뒤**다. 롤백이란 "커밋 전엔 아무도 안 봤다"가 전제인데, 이미 참조되어버렸으니 그 전제 자체가 깨진 거.

DB 이론으로 보면 이는 커밋되지 않은 데이터를 다른 컴포넌트가 읽는 것, 즉 구조적인 dirty read 문제와 같다. RDBMS의 READ UNCOMMITTED보다도 심각한 건, RDBMS는 최소한 락이나 버전 체크로 롤백 시 그 dirty 값을 읽은 트랜잭션도 함께 무효화할 방법이 있지만, 인메모리 카운터가 별도 서비스로 넘어가 버리면 그 참조를 되돌릴 메커니즘 자체가 없다는 점이다.

이 문제를 제대로 풀려면 인메모리에 값을 두는 대신 WAL(Write-Ahead Log) 방식의 멱등 적용이 필요하다.

```
[t0] pickup 이벤트를 durable 로그에 먼저 기록 (fsync 보장)
[t0] 로그 기록 성공 시에만 "확정"으로 간주하고 화면 반영
[t1] 별도 컨슈머가 로그를 읽어 DB 행에 비동기 적용 (idempotent, 재시도 가능)
```

이 구조면 flush가 실패해도 로그에 남아있으니 재시도로 유실은 막을 수 있다. 하지만 "로그 기록 성공 = 확정"으로 보고 화면에 즉시 반영한 값을, 경매장 같은 다른 서비스가 아직 DB에 실제 반영되지 않은 시점에 참조해버릴 수 있다는 **읽기 시점 불일치** 문제는 그대로 남는다. 로그는 유실을 막아줄 뿐, "이 값을 언제부터 신뢰해도 되는가"라는 타이밍 문제는 별개로 풀어야 한다.

## 결론 - 격리가 가장 단순하고 안전한 해법이다

결국 유실을 막는 것(durability)과 다른 서비스가 잘못된 시점의 값을 참조해서 되돌릴 수 없는 액션을 하는 것은 별개의 문제다. 후자는 아무리 아키텍처를 정교하게 짜도 "그 값을 누가 언제 신뢰하고 액션을 취하느냐"에 대한 설계 없이는 풀리지 않는다.

메소처럼 한 번 소비되면 되돌릴 수 없는 자산 값은, 고빈도 쓰기 구간(필드)과 그 값을 기준으로 무거운 크로스 서비스 트랜잭션을 여는 구간(경매장)을 **공간적으로 분리**하는 게 어떤 정교한 이벤트 소싱·WAL 패턴보다도 단순하고 안전한 해법이다.

- **필드**: 메소 증가만 있는, 순수 로컬 동기 트랜잭션 구간으로 유지
- **마을**: 메소 증가·감소가 모두 있을 수 있는, MSA 비동기 트랜잭션이 허용되는 구간

이렇게 나눠두면 필드에서 사냥 중인 유저는 Saga 보상이든 이벤트 유실이든 그 어떤 분산 트랜잭션의 복잡성도 목격하지 않는다는 걸 설계적으로 보장할 수 있다. 결국 이건 "기술적으로 불가능해서"가 아니라, 락 경합보다도 **"유저가 비동기 보정을 목격하게 만들지 않는다"는 UX 일관성**이 더 결정적으로 작용한 설계 선택이라고 보는 게 균형 잡힌 해석이다.

이렇게 보면 이 구조, 은행권 아키텍처 패턴이랑 꽤 닮아 있다. 은행 계정계 코어는 잔액이라는 절대 흔들리면 안 되는 데이터를 다루다 보니 오래되고 보수적인 형태로 유지되고, 포인트·리워드 같은 부가 서비스는 MSA로 분리해 코어 시스템을 API로 "호출"하는 식으로만 접근한다 - 내부 트랜잭션 경계는 침범하지 않고, 바깥에서 정해진 인터페이스로만 두드리는 것. 메이플스토리도 "메소"라는 코어 자산은 사냥터에서 보호(순수 증가만 허용)하고, 감소가 발생하는 무거운 트랜잭션은 마을로 격리해 코어를 보호하면서 서비스를 확장하는 - 결국 비슷한 철학이다.
