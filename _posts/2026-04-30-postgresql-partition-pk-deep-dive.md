---

## UK가 여러 개일 때 파티셔닝이 왜 막히는가

설계하던 테이블이 이런 구조였음.

- **PK**: `data_id` (numeric, 대리키)
- **UK**: `(some_col, timestamp_col, ...)`
- 파티션 기준: `timestamp_col` 기준 yyyy-MM

직관적으로 "UK에는 timestamp가 있으니까 파티션 키 포함됐고, PK에는 없으니까 문제가 생기겠다" 싶었는데, 왜 PostgreSQL이 이걸 막는지까지는 명확하지 않았음.

핵심은 **로컬 인덱스(Local Index)** 구조에 있음.

파티셔닝된 테이블의 인덱스는 파티션별로 쪼개져 독립적으로 존재함. `data_id`만으로 PK(또는 UK)를 잡으면, 새 데이터가 INSERT될 때 `data_id`의 유일성을 보장하기 위해 **존재하는 모든 파티션의 인덱스를 전부 뒤져야 함**. 파티션이 수십 개라면 수십 번의 인덱스 스캔이 생기는 거임.

## Truncate/Drop할 때 생기는 문제 (핵심 논리)

파티셔닝의 가장 큰 이점이 오래된 파티션을 `ALTER TABLE ... DETACH PARTITION` 또는 `DROP`으로 O(1)에 날려버리는 거잖음. 데이터 파일이랑 로컬 인덱스 파일이 같이 통째로 날아가니까 DELETE보다 압도적으로 빠른 거고.

근데 **파티션 키를 포함하지 않는 글로벌 인덱스**가 있었다면?

파티션 파일은 한 번에 날아가는데, 글로벌 인덱스 트리에서는 방금 지운 파티션에 속했던 수백만 건의 노드를 일일이 찾아서 삭제하고 트리를 재정렬해야 함. 파티셔닝의 빠른 폐기 이점이 완전히 날아가는 거임.

**파티셔닝의 이점을 유지하면서 전체 데이터 무결성을 검증하려면 너무 비효율적이기 때문에, DB가 아예 그런 구조를 만들지 못하도록 막는 것.**

## 복합 PK로 해결은 됐는데, 조회 패턴 문제

`(data_id, rgst_dt)`로 복합 PK를 잡으면 파티셔닝 제약은 해결됨. 근데 실제 애플리케이션(JPA/JDBC)에서 `findById(data_id)` 처럼 `data_id`만 조건으로 넘기면?

**파티션 프루닝(Partition Pruning)이 동작하지 않음.**

쿼리에 파티션 키 조건이 없으면 DB는 어느 파티션에 해당 데이터가 있는지 알 수 없음. 결국 모든 파티션에 순차적으로 인덱스 스캔을 날리게 됨. 파티션이 60개면 60번 찌름.

`LIMIT 1`을 걸면 데이터를 찾는 순간 나머지 파티션 탐색을 중단하니까 Best Case에서는 빠를 수 있음. 근데 찾으려는 데이터가 마지막 파티션에 있거나, **아예 존재하지 않는 데이터**를 조회하는 경우엔 모든 파티션을 끝까지 다 뒤짐. API 응답 레이턴시가 요청마다 10ms에서 1초 넘게 튀는 구조가 되는 거임.

## JPA는 왜 대리키를 권장하는가

파티셔닝 제약이 있는데도 JPA/Spring Data가 단일 대리키를 권장하는 이유는 명확함.

- **불변성**: 자연키(날짜, 이메일 등)는 비즈니스가 바뀌면 같이 바뀔 수 있음. 대리키는 레코드가 살아있는 동안 절대 안 바뀜. FK로 참조하는 자식 테이블이 여럿이라면 키 변경의 파급력이 엄청남.
- **연관관계 단순화**: 복합 PK면 FK도 복합키를 들고 다녀야 하고, JPA 엔티티 코드가 `@IdClass`나 `@EmbeddedId`로 복잡해짐.
- **영속성 컨텍스트**: JPA 1차 캐시는 식별자로 엔티티를 관리함. 단일 `Long` 타입이 해시 키로 압도적으로 단순하고 빠름.

JPA의 대리키 권장은 **일반적인 OLTP 테이블**에 맞는 황금률이고, 파티셔닝이 필요한 대용량 이력성 테이블은 다른 판단이 필요한 거임.

## 제대로 된 설계 패턴 찾기

이런 구조를 설계하면 파티셔닝 제약을 완벽하게 충족함.

```sql
CREATE TABLE tb_gme_arcd_rnk_x (
    data_id         BIGINT NOT NULL,
    agrgt_base_dt   TIMESTAMP NOT NULL,
    cust_id         VARCHAR(15) NOT NULL,
    arcd_cmpg_id    BIGINT NOT NULL,
    agrgt_rslt_score BIGINT,
    game_rslt_rnk_val BIGINT,
    max_rslt_rnk_val  BIGINT,
    PRIMARY KEY (data_id, agrgt_base_dt),
    UNIQUE (arcd_cmpg_id, agrgt_base_dt, cust_id)
) PARTITION BY RANGE (agrgt_base_dt);
```

| 제약조건 | 파티션 키 포함 여부 |
|---|---|
| PK (data_id, agrgt_base_dt) | ✅ |
| UK (arcd_cmpg_id, agrgt_base_dt, cust_id) | ✅ |

모든 유니크 제약조건이 파티션 키를 포함하니까 생성 에러 없음. "특정 캠페인 + 기준일 + 고객은 집계 결과가 하나여야 한다"는 비즈니스 룰도 UK로 깔끔하게 방어됨.

다만 이 설계가 제대로 동작하려면 조회 쿼리에 **무조건 `agrgt_base_dt` 조건이 같이 와야 함**. 다행히 "이번 달 내 랭킹", "특정 날짜 랭킹"같은 쿼리 패턴이 자연스럽게 날짜를 포함하니까 이 테이블은 맞아 떨어짐.

## 결론: 어떤 테이블에 파티셔닝을 쓸 것인가

결국 도달한 설계 원칙은 이거임.

| 테이블 유형 | 전략 |
|---|---|
| 기본(마스터) 정보 | 단일 대리키 PK, JPA 이점 최대화 |
| 대용량 내역/이력 데이터 | 복합 PK (대리키 + 파티션 키), 온라인 조회 최소화 |

내역성 데이터는 거의 대부분 날짜 정보가 붙어있을 수밖에 없음. 이걸 온라인에서 실시간으로 마구 뒤지는 게 아니라, 배치에서 인덱스 기반으로 처리하는 구조를 잡으면 파티셔닝의 이점(빠른 폐기, 파티션별 관리)을 제대로 누릴 수 있음.
 > 안붙어있으면 고민도 하지말고 뒤도 돌아보지말고 멀티 키로 조회 하자;
 
파티셔닝이 마법처럼 모든 걸 빠르게 해주는 게 아니라, **쿼리 패턴과 테이블 성격에 맞게 설계했을 때만 제 성능이 나온다**는 게 이번에 제대로 이해한 핵심임.
