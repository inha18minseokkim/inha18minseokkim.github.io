## Q1. `httpclient.pool.max-connections: 500` 이것을 설정함으로써 얻는 것?

동료한테 "netty 커넥션풀 함부로 건들면 백엔드 터질 수 있다"는 피드백 받고 다시 파봤다.

500은 사실 백엔드 캐파를 재서 정한 값이 아니었다. 2부에서 `stock-mediation` outbound `WebClientConfig.kt`가 `maxConnections`를 안 정해줘서 Reactor Netty 기본값(`availableProcessors() * 2`) 쓰다가 `pending acquire queue has reached its maximum size of 32`(`PoolAcquirePendingLimitException`)로 터진 거 고치면서 넉넉하게 잡은 숫자였는데, 그거 그대로 SCG `httpclient.pool.max-connections`에도 복붙한 거였음 — ~~"500이면 알아서 되겠지" 하고~~. "우리 클라이언트가 대기열 부족으로는 안 죽는 값"이지 "상대가 500 동시요청 받아도 괜찮다"고 검증된 값이 아니었던 것.

피드백이 맞는 이유는 두 가지였다:

1. **풀 크기가 암묵적인 스로틀 역할을 하고 있었음.** 작은 기본 풀은 의도치 않게 동시에 나가는 요청 수를 눌러주고 있었는데, 500으로 올리면 그 안전판이 없어진다.
2. **reactor-netty `ConnectionProvider`는 풀이 remote address(대상 호스트)별로 잡힌다고 한다.** `stock-mediation`이 여러 다운스트림(stock-customer-service, overseas-stock-service 등)을 부르는 구조라, 요청 하나가 내부적으로 여러 다운스트림을 병렬로(코루틴 fan-out, 1부 참고) 호출하면 SCG에서 순간적으로 500개 요청 들어왔을 때 다운스트림 쪽 동시 커넥션은 500 × N배로 증폭될 수 있다.

그래서 500이라는 숫자 자체를 낮추기보다 **검증이 안 됐다는 사실 자체가 문제**라는 쪽으로 결론냄. `stock-mediation`이 실제로 안정적으로 받아낼 수 있는 동시 요청 수(자체 DB/r2dbc 풀, 다운스트림 실측 캐파)를 먼저 재고, 그 값 이하로 풀 상한을 잡은 다음, 순간 버스트는 `acquire-timeout`/`pendingAcquireMaxCount`로 큐잉해서 흡수하는 쪽으로 다시 잡아야 함. `stock-gateway → stock-mediation` 풀이랑 `stock-mediation → 다운스트림` 풀은 서로 다른 hop을 캡하는 별개 값인데, 같은 500을 그냥 복붙한 건 나중에 또 문제가 될 수 있어서 이 부분도 다시 손볼 예정..

### 풀을 키우면 어떤것이 달라질까

풀이 작을 때는 SCG 자신의 커넥션 풀이 금방 차서 초과분은 대기하다가 `acquire-timeout`(5000ms) 넘기면 SCG가 스스로 에러를 내며 끊어버렸다. **SCG가 진입 제어 역할을 겸하고 있었던 것** — 백엔드가 감당 못 할 양은 애초에 SCG 선에서 걸러지고 도달을 안 함.

풀을 500으로 넉넉하게 열면 어지간한 트래픽에서는 이 상한에 거의 안 걸리므로 SCG는 실질적으로 대부분의 요청을 다 열어서 보내버린다. **"너무 많다"를 판단하고 쳐내는 역할이 그대로 백엔드로 넘어가는 것.** 백엔드가 그 유입량을 자기 스레드/DB풀/다운스트림 캐파로 못 받아내면, SCG처럼 "풀 꽉 찼다"는 깔끔한 에러 신호 대신 응답 지연, 타임아웃 같은 걸로 좀 더 지저분하게 무너질 수 있음(물론 Advice를 선언해놔서 표준 응답으로 나가긴 하겠지만).

즉 풀 크기를 올린 게 문제를 없앤 게 아니라, **문제를 처리하는 위치를 게이트웨이에서 백엔드로 옮긴 것**에 가깝다. 그러므로 각 레이어간 어떤 역할을 하는지 명확하게 역할 분배를 하고 가는것으로 마무리했다.

## Q2. `max-idle-time`이 설정돼 있어도, 곧 끝날 커넥션을 재사용하려는 순간 왜 타이머를 갱신 안 하고 그냥 끊기나?

이거 물어보기 전까진 그냥 "타이머 갱신 안 하는 버그인가" 싶었는데 아니었다. 클라이언트가 풀에서 커넥션을 다시 꺼내 쓰기로 결정하는 순간이랑, 서버가 그 재사용 사실을 실제로 알아차리는 순간이 같은 시점이 아니기 때문에 거절나는 것 이었다.

- 클라이언트 쪽 idle 타이머는 이미 제대로 동작하고 있음. `SimpleDequePool`(reactor-pool)을 까보면(클로드한테 시킴) eviction predicate가 백그라운드 스윕뿐 아니라 **acquire 시점에도 체크**됨. 클라이언트 자신의 `max-idle-time`을 이미 넘긴 커넥션은 애초에 꺼내주지도 않고 그 자리에서 버리고 새로 만든다.
- 근데 연결을 끊는 주체는 서버다. 서버는 "마지막으로 이 소켓에서 바이트를 본 시점" 기준으로 자기 혼자 카운트다운을 돌리고 있고, 클라이언트가 재사용을 마음먹는 순간엔 서버한테 아무 신호도 안 감. 서버 타이머가 리셋되려면 실제로 바이트가 서버에 도달해야 하는데, 그게 바로 지금 보내려는 요청임. 아직 안보냈다는것;;

순서로 쓰면:

```
1. 클라이언트: "이 커넥션 idle-time 안 넘었네" → 재사용 결정, 쓰기 시작
2. 요청이 네트워크를 타고 서버에 도착
3. 서버가 바이트를 받아야 비로소 서버 쪽 타이머가 리셋
```

1이랑 3 사이 네트워크 왕복 시간 동안 서버 타이머가 먼저 만료돼서 소켓을 닫아버리면, 클라이언트가 아무리 "아직 유효하다" 판단했어도 이미 늦은 거.

"미리 한 번 찔러보고(ping/heartbeat) 살아있는지 확인한 다음 쓰면 되지 않나" 싶을 수도 있는데, 그러면 재사용할 때마다 왕복(RTT)이 하나 더 붙는다. 커넥션 풀 쓰는 이유 자체가 매 요청마다 TCP/TLS 핸드셰이크 비용 없애려는 건데, 재사용마다 확인용 왕복 추가하면 그 이득이 상당히 상쇄된다. 그래서 reactor-netty 포함 대부분 HTTP keep-alive 풀이 기본적으로 이런 사전 검증(probe)을 안 한다고 함.

리셋할 공유 타이머 자체가 없다는 게 결론. 그래서 3부에서 한 게 "타이머를 갱신하는" 방법이 아니라, hop마다 클라이언트 idle-timeout을 서버 idle-timeout보다 확실히 짧게(여유 두고) 잡아서, 클라이언트가 재사용 판단하는 시점엔 서버가 아직 자기 타이머를 안 채웠을 확률을 최대한 높이는 순서 설계였다. 레이스를 완전히 없애는 게 아니라 발생 확률을 실질적으로 0에 가깝게 낮추는 거고, 그럼에도 남는 극히 작은 확률은 SCG의 premature-close 1회 재시도 로직이 핸들링한다고 보면 된다(백만번 빡세게 호출해도 한번 날까 말까긴 하지만, 그마저도 핸들링됨).

## Q3. reactor-netty가 조용히 재시도하던 말던 아무튼 HTTP 최종 응답은 항상 200인데, eBPF는 왜 그걸 499로 잡나? 소켓 레벨로 설명하면?

3부에선 결론만 짧게 냈던 부분인데, 소켓 syscall 타임라인으로 다시 짚어봤다.

`opentelemetry-ebpf-instrumentation`(구 Beyla)은 JVM 바이트코드나 reactor-netty 내부 재시도 로직을 아예 못 본다. 커널의 `connect()`/`write()`/`read()`/`close()` syscall만 후킹해서 "파일 디스크립터(fd) 하나 = 트랜잭션 하나"로 재구성하는 방식. 관측 단위가 소켓이라는 게 우리가 보는것(L7) 과 다르다.

풀에 있던 커넥션 C1(fd=17)이 idle-time 마진 안이라 재사용됐다고 하면:

```
t=39.800  서버가 idle-timeout 도달, FIN(혹은 RST) 전송 → 소켓 종료 시작
t=39.850  클라이언트 pool: "C1, 아직 안 넘었네" → C1 재사용 결정
t=39.851  write(fd=17, "GET /...")   ← 상대가 이미 닫았어도 로컬 write()는
                                        보통 즉시 실패 안 하고 일단 성공함
t=39.870  read(fd=17) → 0 bytes(EOF) 또는 ECONNRESET
                                        ← 응답 바이트를 한 개도 못 받고 종료 확정
t=39.871  close(fd=17)
```

eBPF는 딱 여기까지만 본다고 한다(볼 수 밖에 없다고 한다). fd=17 위에서 `write()`(요청 전송)는 있었는데 그에 대응하는 `read()`가 정상 응답 없이 EOF/리셋으로 끝났다 → "요청은 나갔는데 응답을 하나도 못 받고 끊겼다"는 패턴이고, nginx가 "클라이언트가 응답 받기 전에 연결을 끊음"을 뜻하는 데 오래 써온 코드(HTTP표준은 아닌데 많이 씀) **499**를 그대로 합성한다. (진짜 HTTP 상태줄이 온 게 아니라 파싱할 status code가 없어서, 이 상황 표현할 sentinel 값으로 이미 관행처럼 쓰이던 499를 재사용하는 것. 먼저 끊은 쪽이 서버인지 클라이언트인지는 syscall만으론 구분 못 해서 그냥 같은 버킷에 넣는 거라고 함.)

그 직후 JVM 안에서는 조용히 새 소켓을 연다:

```
t=39.872  connect() → 새 소켓 C2(fd=23)
t=39.910  write(fd=23, "GET /...")
t=39.980  read(fd=23) → 200 OK + 정상 바디
t=39.981  close(fd=23) 혹은 pool 반환
```

eBPF 입장에선 fd=17이랑 fd=23은 완전히 남남인 두 개의 독립된 소켓 이벤트다. "이건 같은 비즈니스 요청의 1차 시도랑 2차 시도(재시도)다"라는 논리적 연결은 reactor-netty의 `retryWhen` 체인 안, 그러니까 JVM 메모리상의 Reactor 연산자 그래프에만 있고, syscall 레벨엔 흔적이 안 남음. 그래서 Tempo엔 `span #1: fd=17, 499`랑 `span #2: fd=23, 200`이 서로 무관한 두 트랜잭션으로 나란히 남는다. 소켓 레벨 관측이랑 애플리케이션 레벨 재시도 사이에 이 간극이 있어서 생기는 노이즈다.

기존 java agent에서 jar 주입을 통해 opentelemetry를 사용하는 경우에는 어플리케이션 함수 콜하는 레이어까지 다 알 수 있었지만, Beyla는 네트워크 IO만 볼 수 있기 때문에 기존처럼 완벽한 재구성이 안되는 것 같다.

이게 Beyla(정확히는 이름 바뀐 opentelemetry-ebpf-instrumentation)라서 생기는 문제라기보단, **eBPF 기반 계측 방식 자체의 구조적인 문제**였던 거였다. 자바 쪽엔 바이트코드를 직접 조작하는 `opentelemetry-java-instrumentation`(그 `-javaagent`로 붙이는 agent)이 따로 있고, 여기엔 `netty-4.1`, `reactor-netty-1.0` 계측 모듈이 있어서 `retryWhen` 체인 안쪽까지 계측 대상이 된다고 한다. 이 방식이면 재시도 span을 애플리케이션이 스스로 알고 있는 상태에서 parent-child로 엮어낼 수 있으니까 지금 겪은 fd=17/fd=23 노이즈 자체가 안 생겼을 것. 결국 agent 기반(bytecode) vs eBPF 기반(syscall) 계측의 트레이드오프고, 언어 무관하게 코드 수정 없이 붙일 수 있다는 장점 대신 이런 애플리케이션 레벨 상관관계는 놓치는 셈인듯.

## Q4. 근데 그 설명대로면 재시도가 그만큼 자주 났을 텐데, DEBUG 로그는 왜 거의 안 남았나?

이건 물어보고 나서야 걸린 부분인데, 찝찝하다..

지금까지 확인한 두 후보를 나란히 놓으면:

| 후보 메커니즘 | 로그 위치 | 실측 결과 |
|---|---|---|
| acquire 시점에 죽은 채널 감지 | `DefaultPooledConnectionProvider`의 `"Immediately aborted pooled channel..."` (DEBUG) | 계속되는 Tempo 499에 비해 **한 번도 안 찍힘** |
| 애플리케이션 자체 재시도 | `WebClientManager`의 `[WebClientManager][retry]` (직접 추가한 진단 로그) | 수백만 건 호출 중 **1건만** 찍힘 |

둘 다 계속되는 499 건수에 비해 압도적으로 적다. Q3에서 그린 그림이 우리가 아는 두 로그 자리 중 어느 쪽으로도 설명이 안 된다는 뜻.

Q3 결론이 틀렸다는 얘긴 아님 — 애플리케이션 최종 응답이 항상 200이고, 앱 로그 어디에도 에러가 없고, 특정 서비스에 국한 없이 무차별적으로 발생한다는 관측 패턴 자체는 여전히 저 그림이랑 앞뒤가 맞는다. 문제는 정확히 reactor-netty 안쪽 **어디서** 이 조용한 복구가 일어나는지를 아직 못 짚었다는 것.

그래서 세 번째 후보로 `HttpClientConnect$HttpObserver.onUncaughtException()`(connection-reset 시 1회 재시도, `AbortedException.isConnectionReset()` 체크 후 헤더/바디가 아직 안 나갔으면 DEBUG로 `"the request will be retried"`, 이미 나갔으면 WARN으로 `"...cannot be retried..."`)를 찾아서 `reactor.netty.http.client.HttpClientConnect: DEBUG` 켜고 지켜보는 중인데, 지금까진 같은 클래스의 다른 이벤트(`HttpIOHandlerObserver.onStateChange()`가 커넥션 핸들러 적용마다 찍는 `"Handler is being applied"`)만 보이고 정작 찾는 로그는 한 번도 안 찍혔다. 지금까지 확인한 후보 세 개가 전부 로그를 거의/전혀 안 남기고 있는 상태.

정황 증거는 강한데 "이거다" 하고 특정할 증거가 아직 없다. 다음엔 Tempo에서 잡히는 499 이벤트 하나의 정확한 시간을 뽑아서 그 구간 Loki 로그를 문자열 필터 없이 통째로 대조해볼 생각이다(언젠간...)

## 정리

이번 편은 새 원인이나 새 조치라기보단, 3부까지 낸 결론이랑 설정값들 다시 검증하고 궁금한 내용들을 다시 짚어보며 정리하는 과정이었다.

- `max-connections: 500`은 "안 죽는 값"이지 "검증된 값"이 아니었음 — 백엔드 실측 캐파 기반으로 다시 잡아야 함.
- `max-idle-time`은 애초에 갱신할 공유 타이머가 없음 — hop별 순서 맞추는 게 유일한 완화책.
- eBPF의 499 합성은 소켓 syscall 레벨에서 보면 말이 됨.
- 근데 그 조용한 복구가 정확히 JVM 어디서 일어나는지는 아직 못 찾음 — 후보 세 개 다 로그가 거의 안 남는다는 것만 새로 확인함.

그리고 499 에러의 경우 왜 하필 500도 아니고 499일까 라는 생각을 해보면 보통 500에러는 정말 인프라 레이어 에러인 경우가 많아(자원부족, 타임아웃 등) 에러의 책임이 인프라 레이어에 있다는것이 거의 명확하지만 400 에러는 사용자가 잘못 호출하는것으로 부터 비롯된 경우가 대부분이다. 따라서 에러가 거절 난 경우 이게 인프라 레이어단 문제이긴 하지만 따지고 보면 어플리케이션 레이어에서 맺고 끊는것을 잘 설정하면 나지 않으니 400과 500 사이 어딘가인데 어플리케이션 개발자에게 해당 책임을 넘긴기는 뉘앙스가 아닌가 싶다? 그러다보니 이 에러를 해결하기 위해 개발자인 내가 삽질을 한것과 같은 이치인것..
