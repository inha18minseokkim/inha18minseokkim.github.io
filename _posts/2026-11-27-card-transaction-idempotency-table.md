럭키드로우에 체크카드 결제하면 응모권 주는 기능을 붙였는데, 결제 내역 테이블이 거래일자 월 파티션이다. 근데 정작 거래를 찾는 쪽이 거래일자를 모르는 경우가 있었음..

파티션 키가 왜 PK에 들어가야 하는지는 [이전 포스팅]({% post_url 2026-04-30-postgresql-partition-pk-deep-dive %})에서 정리했는데, 이번엔 그 규칙 때문에 생긴 문제를 어떻게 피했는지에 대한 이야기다.

---

## 원래 구조

- 결제 내역 `CRD_TX_X`
  - PK: `(혜택이벤트식별자, 거래구분, 거래고유번호, rgst_dt)`
  - `rgst_dt`(거래일자) 기준 월 파티션
  - 인덱스: `ix_01 (cust_id, rgst_dt)`, `ix_02 (혜택이벤트식별자, 원거래고유번호)`
- 카드로 지급한 응모권 `TCKT_OCR_X`
  - 이것도 `rgst_dt` 월 파티션인데 값이 **처리일**(지급한 날)

승인은 체크카드 서버가 `POST`로, 취소는 원승인 거래고유번호를 들고 `PUT`으로 들어온다.

## 뭐가 문제였냐

| No | 문제 | 원인 |
|---|---|---|
| 1 | 원거래 조회가 전 파티션 | 취소 요청에는 취소 자기 거래일자만 있고 **원승인 거래일자가 없음**. `rgst_dt` 조건을 못 건다 |
| 2 | 중복 확인, 선취소 확인이 전 파티션 | "이미 처리한 거래냐", "이 승인을 취소하는 건이 먼저 왔냐"를 날짜 없이 찾았음 |
| 3 | 응모권 중복 확인, 취소 대상 잠금이 전 파티션 | 응모권 `rgst_dt`가 처리일이라 결제 내역 날짜로는 못 찾음 |
| 4 | 재전송 방지에 틈 | 아래에서 따로 |
| 5 | 비용이 계속 늘어남 | 파티션이 매달 늘어나니 위 조회 비용도 같이 늘어남 (지금 2026-10 ~ 2028-12, 27개 미리 만들어둠) |

### 재전송을 DB가 못 막는 틈

PostgreSQL은 파티션 테이블의 PK, UNIQUE에 **파티션 키가 반드시 들어가야 한다고 한다.** 그래서 PK가 `(…, 거래고유번호, rgst_dt)`인데, 같은 거래가 **다른 거래일자**로 오면 PK가 달라짐 ㄷ

순서대로 재전송되면 앞에서 조회로 걸러지긴 하는데, 동시에 두 개가 오면 DB가 못 막는다. ~~체크카드 서버가 같은 거래를 날짜 바꿔서 보낼 일이 있겠냐 싶긴 한데~~ 막을 수 있으면 막는 게 맞음.

## 그래서 멱등 테이블을 하나 더 둠

생각은 단순하다. **파티션 없는 작은 테이블에서 "거래 식별자 → 거래일자"를 먼저 찾고**, 파티션 테이블은 그 `rgst_dt`를 걸어서 읽는다. 중복 방지는 이 테이블 PK가 맡음.

`CRD_TX_IDMPT_M` — 거래 1건당 1행, 승인 1행 / 취소 1행.

| 컬럼 | 타입 | 키 | 역할 |
|---|---|---|---|
| bnfs_evnt_id | VARCHAR(20) | PK | 혜택이벤트식별자 |
| card_tx_ds_cd | VARCHAR(20) | PK | `APPROVAL` / `CANCEL` |
| tx_unq_nbr | VARCHAR(20) | PK | 거래고유번호 |
| rgst_dt | VARCHAR(8) | | 결제 내역의 `rgst_dt`(거래일자). 파티션 테이블 찾아가는 값 |
| orgnl_tx_unq_nbr | VARCHAR(20) NULL | | 취소 건만. 취소할 승인의 거래고유번호 |
| del_abl_dttm | TIMESTAMP | | 삭제가능일시 = 거래 발생일 + 90일 0시 |
| 감사 컬럼 6개 | | | 공통 |

- PK에 날짜가 없으니 **거래일자가 달라도 같은 거래면 PK 위반**이 난다. 4번 틈이 여기서 막힘
- 고객식별자, 결제 금액은 안 둔다 (개인정보)
- insert만 하고 값을 안 바꾸니까 이력(`_M_H`) 테이블은 안 만듦

### 같이 바꾼 것

| 항목 | 이전 | 이후 |
|---|---|---|
| 중복 방지 | `CRD_TX_X` PK (거래일자 포함) | 멱등 테이블 PK (거래일자 없음) |
| 거래 조회 | 결제 내역을 PK 앞 3컬럼으로 검색 | 멱등 테이블에서 `rgst_dt` 확인 → 결제 내역을 PK 전체로 조회 |
| 선취소 확인 | `CRD_TX_X ix_02` | 멱등 테이블 `ix_01` |
| 카드 지급 응모권 `rgst_dt` | 처리일 | **거래일자** (결제 내역이랑 같은 값) |
| 응모권 조회 조건 | 발생유형 + 원천 | 발생유형 + 원천 + `rgst_dt` |

응모권 `rgst_dt`를 거래일자로 맞춘 게 은근 중요함. 연결된 행끼리 `rgst_dt`가 같으면 멱등 테이블에서 한 번 알아낸 날짜로 **결제 내역이랑 응모권 둘 다** 프루닝할 수 있다.

## 처리 흐름

저장은 한 트랜잭션에서 **멱등 행 insert → 결제 내역 insert** 순서. 같은 거래가 이미 있으면 결제 내역 적재 전에 PK 위반(`DuplicateKeyException`)이 나고 전체 롤백 → `DUPLICATE_TRANSACTION`으로 응답한다.

**승인 `POST /card/offers`**

1. 회원 확인
2. 중복 확인 — 멱등 테이블 PK. 행 없으면 결제 내역은 아예 안 읽음
3. 선취소 확인 — 멱등 테이블 `ix_01`. 취소가 먼저 와 있으면 승인 이력만 남기고 `ALREADY_CANCELED`
4. 멱등 행 + 결제 내역 저장
5. 지급 대상이면 응모권 중복 확인(`rgst_dt` = 거래일자) 후 지급

**취소 `PUT /card/offers/{originalTransactionNo}`**

1. 회원 확인
2. 취소 거래 중복 확인 — 멱등 테이블 PK
3. 원승인 조회 — 멱등 테이블 PK로 `rgst_dt` 확인 → 결제 내역 PK 전체 조회. 없거나 고객이 다르면 `ORIGINAL_NOT_FOUND`
4. 원승인 시즌이 지났으면 `EXPIRED`
5. 원승인 `rgst_dt`로 지급 응모권 `FOR UPDATE` 잠금 → 남은 응모권만 취소
6. 취소의 멱등 행 + 결제 내역 저장

```
취소 요청 (원거래고유번호만 있음)
   │
   ▼
CRD_TX_IDMPT_M  ── PK 조회 ──▶ rgst_dt
                                  │
              ┌───────────────────┴───────────────────┐
              ▼                                       ▼
   CRD_TX_X (PK 전체)                  TCKT_OCR_X (발생유형·원천·rgst_dt)
   해당 월 파티션 1개                    해당 월 파티션 1개
```

## 인덱스

멱등 테이블

| 이름 | 컬럼 | 쓰는 곳 |
|---|---|---|
| PK | (bnfs_evnt_id, card_tx_ds_cd, tx_unq_nbr) | 재전송 방지, 거래의 `rgst_dt` 찾기 |
| `ix_01` | (bnfs_evnt_id, orgnl_tx_unq_nbr) | 승인 처리할 때 먼저 온 취소 있는지 |
| `ix_02` | (del_abl_dttm) | 삭제가능일시 지난 행 파기 |

파티션 테이블

| 테이블 | 인덱스 | 변화 |
|---|---|---|
| CRD_TX_X | PK (…, rgst_dt) | 유지. 이제 4개 컬럼 다 걸어서 조회함 |
| CRD_TX_X | `ix_01 (cust_id, rgst_dt)` | 유지. 고객 데이터 파기용 |
| CRD_TX_X | `ix_02 (bnfs_evnt_id, orgnl_tx_unq_nbr)` | **삭제**. 멱등 테이블 `ix_01`로 옮김 |
| TCKT_OCR_X | `ix_01 (tckt_ocr_tp_cd, tckt_ocr_src_id)` | 유지. 쿼리에 `rgst_dt` 조건만 추가 |

`TCKT_OCR_X` 인덱스에 `rgst_dt`를 안 넣은 이유는, 프루닝은 인덱스가 아니라 **쿼리 `WHERE`의 파티션 키 조건**으로 정해지기 때문이다. 파티션이 1개로 줄면 그 안에서는 기존 인덱스로 충분함.

## 그래서 몇 개 타냐

정리하면 원칙은 이거임.

- 파티션 테이블 읽기 전에 **`rgst_dt`를 먼저 알아낸다.** 모르면 파티션 없는 멱등 테이블에서 찾는다
- 연결된 행은 **`rgst_dt`를 같게** 만든다 (결제 내역 = 카드 지급 응모권 = 거래일자)
- 조회만이 아니라 **갱신도 PK `(data_id, rgst_dt)`** 로 한다
- `rgst_dt` 없이 카드 거래, 카드 지급 행을 찾는 쿼리는 새로 안 만든다

"이전"은 코드상 쿼리 조건에 `rgst_dt`가 없었다는 기준이고, "이후"는 임시 PostgreSQL 17 띄워서 `auto_explain`으로 실행 계획 찍어본 값이다.

**승인**

| 단계 | 이전 | 이후 |
|---|---|---|
| 중복 확인 | CRD_TX_X 전 파티션 | 멱등 테이블만 (결제 내역 0) |
| 선취소 확인 | CRD_TX_X 전 파티션 | 멱등 테이블만 |
| 응모권 중복 확인 | TCKT_OCR_X 전 파티션 | 1개 |

**취소**

| 단계 | 이전 | 이후 |
|---|---|---|
| 취소 거래 중복 확인 | CRD_TX_X 전 파티션 | 멱등 테이블만 |
| 원승인 조회 | CRD_TX_X 전 파티션 | 1개 |
| 지급 응모권 잠금 | TCKT_OCR_X 전 파티션 | 1개 |
| 지급 응모권 저장 (SELECT·UPDATE) | TCKT_OCR_X 전 파티션 | 1개 |

마지막 줄은 처음에 놓쳤던 부분이다. 조회랑 잠금은 1개로 줄였는데 응모권 저장은 `data_id`만으로 갱신하고 있어서 계속 전 파티션을 타고 있었음.. ~~조회만 잘 걸면 끝인 줄 알았다~~ 엔티티 `@Id`를 `(data_id, rgst_dt)` 복합키로 바꿔서 해결함. Spring Data JDBC가 `save()`할 때 `@Id`로 SELECT, UPDATE를 하니까 `@Id`에 파티션 키가 없으면 저장이 프루닝을 못 받는다.

## 파기

파티션 없는 테이블을 하나 더 두면 이게 계속 커지는 게 부담이라, 90일 지난 행은 배치가 지운다.

- 개인정보 파기 배치 마지막 단계에서 `del_abl_dttm`이 실행일까지인 행을 지움
- 1,000건 단위로 PK DELETE, 지우는 순간에도 삭제가능일시를 다시 확인
- 결제 내역(`CRD_TX_X`)은 이 단계에서 안 지운다

## 아직 남은 것

| 구분 | 내용 |
|---|---|
| 승인·취소 동시 도착 | 서로 상대를 못 보면 취소가 `ORIGINAL_NOT_FOUND`로 남고 지급이 유지될 수 있음. 이번에 해결 **안 함** (순서대로 오는 정상 흐름에서는 없음) |
| 90일 뒤의 취소 | 멱등 행이 지워져서 `EXPIRED`가 아니라 `ORIGINAL_NOT_FOUND`로 나감. 어차피 지난 시즌이라 취소할 응모권은 없다 |
| 90일 뒤의 재전송 | 같은 거래일자면 `CRD_TX_X` PK가 막음. **거래일자를 바꿔서** 다시 보내면 막을 게 없다 |
| 거래고유번호 유일성 | 응모권 원천 ID에 혜택이벤트가 없어서, 거래고유번호가 이벤트·고객과 무관하게 유일하다고 가정함. 체크카드 서버랑 확인 필요 |
| 쓰기 비용 | 거래마다 insert 1건, 인덱스 3개 늘어남 |
| 파기 비용 | 파티션이 없으니 DROP이 아니라 DELETE로 지움. 거래량 많아지면 vacuum 상태 봐야 함 |

## 배포할 때 확인할 것

1. DDL: 새 테이블 + 인덱스 생성, `CRD_TX_X ix_02` 삭제. 파기 배치는 DDL 적용 뒤에 배포
2. 기존 결제 내역이 있으면 멱등 테이블로 옮겨야 함. 안 옮기면 과거 승인의 취소가 `ORIGINAL_NOT_FOUND`가 된다. 같은 거래가 거래일자만 다른 행으로 두 번 있으면 PK 위반 나니까 먼저 확인

```sql
INSERT INTO gme_own.tb_gme_lttc_crd_tx_idmpt_m
      (bnfs_evnt_id, card_tx_ds_cd, tx_unq_nbr, rgst_dt, orgnl_tx_unq_nbr, del_abl_dttm,
       rgst_id, rgst_guid_id, rgst_dttm, amnn_id, amnn_guid_id, amnn_dttm)
SELECT bnfs_evnt_id, card_tx_ds_cd, tx_unq_nbr, rgst_dt, orgnl_tx_unq_nbr, to_date(rgst_dt, 'YYYYMMDD') + INTERVAL '90 days',
       rgst_id, rgst_guid_id, rgst_dttm, amnn_id, amnn_guid_id, amnn_dttm
  FROM gme_own.tb_gme_lttc_crd_tx_x
 WHERE to_date(rgst_dt, 'YYYYMMDD') + INTERVAL '90 days' >= CURRENT_DATE;
```

3. 기존 카드 지급 응모권 중 `rgst_dt`가 승인 거래일자랑 다른 행은 취소할 때 못 찾음. 배포 전에 확인하고 보정

확인한 범위는 H2(PostgreSQL 모드) 테스트로 저장, 2단계 조회, 선취소, 날짜 다른 재전송 차단, 취소 후 승인 `ALREADY_CANCELED`까지 봤고, 파티션 개수는 임시 PostgreSQL 17 실행 계획으로 확인했다. 데이터가 몇 건 안 돼서 **어떤 인덱스를 고르는지랑 응답 시간은 아직 못 봤음.** 위 backfill SQL도 실제 데이터에는 안 돌려봤다.

## 마무리

| 문제 | 해결 |
|---|---|
| 원거래 조회가 전 파티션 | 멱등 테이블이 `rgst_dt`를 알려줘서 1개 |
| 중복·선취소 확인이 전 파티션 | 파티션 없는 테이블 인덱스 조회 |
| 응모권 확인·잠금·저장이 전 파티션 | 지급 행 `rgst_dt` = 거래일자 + 복합키 갱신 |
| 거래일자 다른 재전송을 DB가 못 막음 | PK에서 날짜를 빼서 DB가 막음 (멱등 행 남아있는 동안) |
| 파티션 늘수록 비용 증가 | 승인·취소 경로는 파티션 수랑 무관 |
| 파티션 없는 테이블이 계속 커짐 | 90일 지난 행 배치로 삭제 |

결국 파티션 테이블은 **찾는 쪽이 날짜를 아느냐**가 전부인 것 같다. 모르면 날짜를 알려줄 작은 테이블을 하나 두는 게 제일 싸게 먹힘. 근데 90일 넘어서 날짜 바꿔 오는 재전송은 여전히 못 막는 거라.. 이건 체크카드 서버랑 얘기를 좀 해봐야
